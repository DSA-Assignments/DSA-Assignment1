What to Push / Commit

Push:

All .bal source files
Ballerina.toml / Ballerina.lock (lock file, since it pins dependency versions for everyone)
.proto file
docs/ content (sample payloads, notes)
README.md

Never push (put in .gitignore):

target/ — Ballerina's build output, regenerated by anyone who runs bal build
generated/ — gRPC-generated stubs from the .proto (auto-created on build)
Config.toml — if anyone adds local secrets/config, this shouldn't be shared
.idea/, *.iml, .vscode/ — personal editor settings
.DS_Store
Git Workflow
Clone once, then branch per task:
   git checkout -b feature/q1-asset-crud

Name branches after the task, e.g. feature/q1-maintenance, feature/q2-proto, feature/q2-guest-server.

Commit in small, clear steps:
   git add .
   git commit -m "feat(q1): add asset CRUD endpoints"

Prefix with feat, fix, docs, or chore, and note the question (q1/q2) so history stays readable across 8 people.

Push your branch, not straight to main:
   git push origin feature/q1-asset-crud
Open a Pull Request into main so at least one other teammate reviews before merging — this catches conflicts (especially around the shared data models / proto) early.
Pull before you start each session:
   git pull origin main

to stay in sync, since 8 people are touching the same repo.

Whoever owns Setup & Data (Person 1) and Proto & Setup (Person 5) should merge their branches into main first — everyone else's git pull after that gives them the shared models/proto to build on.
